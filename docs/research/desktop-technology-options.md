# Cross-platform desktop technology and packaging options

Research date: 2026-08-05
Ticket: [Mill1893/rom-manager#13](https://github.com/Mill1893/rom-manager/issues/13)

## Scope and method

This report compares five viable, established implementation paths for a Windows-first local ROM manager: Tauri 2, Electron, Avalonia, Flutter, and Qt 6. The comparison is driven by this product's unusual center of gravity: long-running filesystem and device transfers, durable local operation state, Windows MTP integration, and eventually signed installers for Windows, macOS, and Linux.

Claims marked **Verified** are stated by official project, platform, API, or source-repository documentation. Claims marked **Inference** are engineering conclusions derived from those facts; they should be validated with a product-shaped prototype before a stack decision. Payload and memory figures are deliberately not estimated: dependencies, symbols, rendering backend, architecture, installer compression, and runtime distribution mode can change them substantially.

This report informs a later decision; it does not make that decision.

## Requirement baseline

### MTP is a transport boundary, not a mounted filesystem

**Verified:** Microsoft's Windows Portable Devices (WPD) API lets applications enumerate a device, inspect capabilities and objects, and send or receive content; Microsoft supplies drivers for standard MTP and mass-storage devices ([WPD API overview](https://learn.microsoft.com/en-us/windows/win32/wpd_sdk/wpd-application-programming-interface)). The API surface is COM: `IPortableDeviceContent` creates, enumerates, examines, and deletes device content, while `IPortableDeviceResources` exposes raw object data through `IStream` ([portabledeviceapi interfaces](https://learn.microsoft.com/en-us/windows/win32/api/portabledeviceapi/), [`IPortableDeviceResources`](https://learn.microsoft.com/en-us/windows/win32/api/portabledeviceapi/nn-portabledeviceapi-iportabledeviceresources)). `IPortableDeviceDataStream` supports cancelling an in-progress call, and the object ID only becomes valid after committing a newly written stream ([data stream API](https://learn.microsoft.com/en-us/windows/win32/api/portabledeviceapi/nn-portabledeviceapi-iportabledevicedatastream)).

**Inference:** The product should model MTP as a transport adapter with streamed reads/writes, explicit commit/cancel semantics, byte-count progress, and disconnect recovery. Treating an MTP target as an ordinary path would leak false filesystem assumptions into the domain layer. Since WPD targets Windows, a later macOS/Linux device implementation will necessarily be a different adapter even if the transfer-job interface is shared.

### Long-running work and durable state are application concerns

**Verified:** Every candidate offers a supported way to keep blocking or compute-heavy work off the UI thread: Tauri asynchronous commands and channels ([Tauri commands](https://v2.tauri.app/develop/calling-rust/#async-commands)); Electron utility processes ([Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model#the-utility-process)); .NET task-based asynchronous operations ([.NET task-based pattern](https://learn.microsoft.com/en-us/dotnet/standard/asynchronous-programming-patterns/task-based-asynchronous-pattern-tap)); Flutter long-lived isolates with message ports ([Flutter isolates](https://docs.flutter.dev/perf/isolates)); and Qt worker objects on `QThread` with queued signals ([Qt threads](https://doc.qt.io/qt-6/qthread.html#details)).

**Verified:** SQLite is intended for device-local and desktop-application storage, and its transactions remain atomic across application crashes, OS crashes, and power loss ([appropriate uses](https://www.sqlite.org/whentouse.html), [transactional guarantees](https://www.sqlite.org/transactional.html)). It permits many readers but one writer at a time ([appropriate uses](https://www.sqlite.org/whentouse.html#situations_where_a_client_server_rdbms_may_work_better)).

**Inference:** UI toolkit selection does not solve transfer reliability. Whichever candidate is chosen should put copy/MTP work behind an application service, persist job intent and state transitions in short SQLite transactions, write file/device data outside those transactions, expose cooperative cancellation, and reconstruct interrupted jobs on restart. One serialized persistence writer is compatible with SQLite's concurrency model and simplifies crash recovery.

## Detailed candidate analysis

### Tauri 2

#### Runtime footprint and native model

**Verified:** Tauri uses the operating system's WebView and compiles its Rust backend into the application rather than shipping a browser runtime of its own ([architecture](https://v2.tauri.app/concept/architecture/)). On Windows the installer must still ensure WebView2 exists. Microsoft says the Evergreen runtime is included in Windows 11 and is present on most Windows 10 systems, but applications should detect and install it when absent; a fixed-version runtime adds more than 250 MB according to Microsoft's current distribution documentation ([WebView2 distribution](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)). Tauri's installer supports downloaded/embedded bootstrapper, offline, fixed-runtime, and skip modes ([Tauri WebView2 options](https://v2.tauri.app/distribute/windows-installer/#webview2-installation-options)).

**Inference:** A normal Evergreen deployment has the smallest app-owned browser payload among the web-UI candidates, but offline installation changes that result sharply. A representative signed installer should therefore be measured in both online and offline modes rather than quoting a single "Tauri size." System WebViews also mean rendering and web-platform behavior vary by OS and installed runtime.

**Verified:** For WPD, the in-process path can be a Windows-only Rust module using Microsoft's generated Win32/COM bindings. The `windows` crate provides C-style, COM, and WinRT projections, while `windows-core` supplies COM type support ([windows-rs crate guide](https://github.com/microsoft/windows-rs#choosing-your-crates)). Tauri can alternatively bundle an architecture-specific helper executable and exchange progress over its child-process channel ([sidecars](https://v2.tauri.app/develop/sidecar/)).

#### Persistence, security, and testing

**Verified:** The official SQL plugin supports SQLite on Windows, macOS, and Linux, includes transactional migrations, and blocks dangerous commands until capabilities enable them ([SQL plugin](https://v2.tauri.app/plugin/sql/)). Tauri's capability files restrict which WebViews can call core/plugin operations; bundled code gets API access by default while remote sources require explicit grants ([capabilities](https://v2.tauri.app/security/capabilities/)). Application-defined commands need separate manifest configuration if they should not be callable from every window ([capabilities, command note](https://v2.tauri.app/security/capabilities/#core-permissions)).

**Inference:** Persistence and transfer orchestration should stay in Rust rather than exposing arbitrary SQL or filesystem primitives to the frontend. A narrow API such as `startTransfer`, `cancelTransfer`, and `subscribeToJob` makes the capability model useful; granting generic write SQL and broad filesystem scope would weaken it.

**Verified:** Tauri supports unit/integration tests with a mock runtime and end-to-end WebDriver tests. Its documentation notes WebDriverIO support across Windows, Linux, and macOS, while direct protocol driving is limited by the absence of a macOS desktop WebDriver client ([testing](https://v2.tauri.app/develop/tests/)).

#### Maintenance trade-off

**Inference:** The application owns Rust, frontend JavaScript/TypeScript, WebView IPC contracts, WebView compatibility, and platform-specific WPD code. In return, it gets memory-safe systems code, explicit frontend privilege scoping, and broad built-in packaging. This is favorable only if the team is comfortable maintaining both Rust and web tooling.

### Electron

#### Runtime footprint and native model

**Verified:** Electron ships an application bundle composed of Electron, Chromium, and Node.js, and its security guidance requires keeping that complete stack current ([security guidance](https://www.electronjs.org/docs/latest/tutorial/security#general-guidelines)). Each window has a renderer process; the main process has Node APIs; preload code exposes selected capabilities through `contextBridge`; utility processes can host CPU-intensive or crash-prone work ([process model](https://www.electronjs.org/docs/latest/tutorial/process-model)).

**Inference:** Because Chromium and Node are app-owned rather than shared from the OS, Electron has the largest baseline payload of these five approaches, but also the most consistent web runtime across desktop platforms. Exact installer and working-set differences need measurement with the actual UI and native bridge.

**Inference:** WPD can be integrated through a C++ Node-API addon or an out-of-process helper. **Verified:** Electron's ABI differs from stock Node, native modules must be rebuilt for Electron and target architecture, and upgrades usually require another rebuild; Forge invokes `@electron/rebuild` automatically ([native modules](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules)).

**Inference:** A small, versioned helper executable can reduce Electron ABI coupling and contain COM/apartment and device-driver failure, at the cost of defining and supervising another IPC protocol. An in-process addon avoids that protocol but puts native crashes in the main process and adds a prebuild matrix.

#### Persistence, security, and testing

**Verified:** Electron itself does not prescribe a database. Its main and utility processes can use Node packages and filesystem APIs ([process model](https://www.electronjs.org/docs/latest/tutorial/process-model#the-main-process)).

**Inference:** SQLite is viable, but choosing a native SQLite package introduces the same Electron ABI/prebuild concern as WPD. Keeping all database access in the main/utility layer and exposing domain operations over validated IPC avoids giving renderer content direct filesystem authority.

**Verified:** Electron defaults to context isolation and renderer sandboxing, but its own checklist still requires local/secure content, restrictive CSP, no Node integration for remote content, sender validation on every IPC message, constrained navigation/window creation, and timely framework updates ([security checklist](https://www.electronjs.org/docs/latest/tutorial/security#checklist-security-recommendations)). Electron explicitly warns that arbitrary untrusted content is a severe risk because application code can reach the filesystem and shell ([security preface](https://www.electronjs.org/docs/latest/tutorial/security#preface)).

**Verified:** Electron does not maintain its own test solution. Its documentation supports WebdriverIO/Selenium, experimental Playwright Electron support, and custom IPC drivers ([automated testing](https://www.electronjs.org/docs/latest/tutorial/automated-testing)).

#### Packaging and maintenance trade-off

**Verified:** Forge's Squirrel maker creates a per-user setup executable plus update metadata; its WiX maker creates traditional MSI packages and is specifically positioned for enterprise distribution requirements ([Squirrel](https://www.electronforge.io/config/makers/squirrel.windows), [WiX](https://www.electronforge.io/config/makers/wix-msi)). Forge makers convert the packaged application into platform-specific artifacts ([makers](https://www.electronforge.io/config/makers)).

**Inference:** Electron has the broadest JavaScript desktop ecosystem and avoids cross-platform WebView differences, but the project must track Electron's release/security cadence, Node dependencies, Chromium behavior, and native rebuilds. Runtime consistency is purchased with payload and update bandwidth.

### Avalonia on .NET

#### Runtime footprint and native model

**Verified:** Avalonia renders its own controls with Skia and runs on .NET across Windows, macOS, and Linux ([overview](https://docs.avaloniaui.net/docs/welcome)). On Windows it calls Win32 directly, uses Direct3D-backed Skia with software fallback, and requires no Windows-specific .NET workload ([Windows integration](https://docs.avaloniaui.net/docs/platform-specific-guides/windows#how-avalonia-runs-on-windows)).

**Verified:** A framework-dependent .NET publish is smaller but requires an installed runtime and automatically rolls forward to installed security patches. A self-contained publish includes the .NET runtime, is larger, and requires the application publisher to ship runtime updates. Native AOT can reduce memory and deployment size but not all libraries/features are compatible ([.NET publishing modes](https://learn.microsoft.com/en-us/dotnet/core/deploying/)). Avalonia supports Native AOT but documents reflection, dynamic XAML/control, and third-party-control limitations ([Avalonia Native AOT](https://docs.avaloniaui.net/docs/deployment/native-aot)).

**Inference:** Self-contained is the safer consumer-install default because it removes a prerequisite, while framework-dependent may suit managed environments. Native AOT should be treated as an optimization experiment after WPD/COM and SQLite compatibility are proven, not assumed at architecture selection time.

**Verified:** .NET explicitly supports COM components and OS APIs through its native interoperability facilities, making WPD reachable from C# through COM interop in the same process ([native interop](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/)).

**Inference:** This has less glue than a Node addon or Flutter plugin and keeps transfer code memory-managed. It still requires deliberate COM apartment/lifetime handling, worker-thread execution, and a platform interface so Windows-only types do not spread through the application core.

#### Persistence, security, and testing

**Verified:** Microsoft provides `Microsoft.Data.Sqlite`, a lightweight ADO.NET provider usable directly or under Entity Framework Core ([provider overview](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/)).

**Verified:** Avalonia has a headless platform with the control tree, layout, styling, data binding, simulated input, and optional rendered-frame capture. It also documents Appium tests against real Windows and macOS windows; Linux lacks a stable Appium desktop driver ([headless testing](https://docs.avaloniaui.net/docs/testing/setting-up-the-headless-platform), [Appium](https://docs.avaloniaui.net/docs/testing/ui-testing-with-appium)).

**Inference:** Unlike a webview stack, a normal Avalonia app has no renderer-to-native privilege bridge to configure. UI and backend code normally share process privileges, so least privilege must come from module APIs, careful path validation, OS packaging, and optionally a helper process for risky native/device work. This is simpler but not equivalent to a sandbox.

#### Packaging and maintenance trade-off

**Verified:** Avalonia's current platform policy gives full Tier 1 testing only to selected current Windows/macOS/Linux releases, with older versions at Tier 2 best-effort or Tier 3 commercial-only ([support tiers](https://docs.avaloniaui.net/docs/supported-platforms)). Its macOS and Linux deployment guides either use Avalonia Parcel or require explicit bundle/package assembly; Windows can package any desktop app with MSIX, whose signed packages provide clean install/uninstall, update, integrity, and optional container behavior ([Avalonia macOS](https://docs.avaloniaui.net/docs/deployment/macos), [Avalonia Linux](https://docs.avaloniaui.net/docs/deployment/linux), [MSIX](https://learn.microsoft.com/en-us/windows/msix/overview)).

**Inference:** The core development stack is cohesive for C#/.NET teams, but release engineering spans `dotnet publish`, platform packaging/signing, and potentially Avalonia-specific tooling. The intended minimum Windows version must be reconciled with Avalonia's support tier before committing.

### Flutter

#### Runtime footprint and native model

**Verified:** Flutter compiles desktop applications for Windows, macOS, and Linux, including native platform runner code and plugins ([desktop support](https://docs.flutter.dev/platform-integration/desktop)). Release Dart code is AOT compiled and the app ships Flutter's graphics engine rather than an OS WebView ([Flutter source overview](https://github.com/flutter/flutter#fast-results)).

**Inference:** Its payload is self-contained and avoids browser variability, but includes an engine and native runner, so it should be expected to sit between system-WebView Tauri and bundled-Chromium Electron for a small app. This is a hypothesis to measure, not a guaranteed ordering once real assets and dependencies are present.

**Verified:** For WPD, the normal desktop plugin path uses a C++ Windows implementation and asynchronous platform-channel messages ([platform-specific code](https://docs.flutter.dev/platform-integration/platform-channels#overview)). FFI is another option: Flutter can generate C-ABI bindings, compile and bundle native code through build hooks, or dynamically load a Windows system DLL ([FFI](https://docs.flutter.dev/platform-integration/bind-native-code)).

**Inference:** WPD's COM interface is not a C ABI, so either a C/C++ wrapper exposed through FFI or a C++ platform plugin is still required. The latter aligns with Flutter's Windows runner and can report progress over channels, but creates a Dart/C++ contract and platform-specific test surface.

#### Persistence, security, and testing

**Verified:** Flutter's official SQLite recipe uses the third-party `sqflite` plugin and explicitly supports only macOS, iOS, and Android, not Windows or Linux ([SQLite recipe](https://docs.flutter.dev/cookbook/persistence/sqlite)). Desktop-wide persistence therefore requires another package/FFI binding or application-owned wrapper.

**Verified:** Dart isolates have independent memory and communicate by messages. Long-lived isolates are intended for repeated or long-running processes and can use platform plugins, but background isolates cannot receive unsolicited host-platform messages ([isolates](https://docs.flutter.dev/perf/isolates)).

**Inference:** A transfer plugin should own its native worker and send progress to the main isolate, rather than depending on unsolicited callbacks into a background isolate. As with Avalonia and Qt, native plugins run with application privileges; Flutter provides API separation, not an Electron/Tauri-style web-content privilege boundary.

**Verified:** Flutter has first-party unit, widget, and whole-app integration test support. Its `integration_test` package cannot interact with native platform UI such as permission dialogs or platform views, so native interactions need another harness ([testing overview](https://docs.flutter.dev/testing/overview)).

#### Packaging and maintenance trade-off

**Verified:** Flutter's Windows release guide focuses on Microsoft Store/MSIX and uses the external `msix` Dart package in its documented automation; its Linux guide focuses on Snapcraft and lists third-party alternatives; macOS distribution uses Xcode signing/archive flows ([Windows](https://docs.flutter.dev/deployment/windows), [Linux](https://docs.flutter.dev/deployment/linux), [macOS](https://docs.flutter.dev/deployment/macos)).

**Inference:** Packaging is viable but less single-tool than Tauri's bundler or Electron Forge. Maintenance spans Flutter/Dart, a C++ Windows plugin, a desktop SQLite binding, and platform installer tooling. Flutter's excellent widget-test layer does not remove the need for Windows hardware integration tests around WPD.

### Qt 6

#### Runtime footprint and native model

**Verified:** Qt applications can use shared libraries or static linking. Static linking produces fewer deployment files but larger, less flexible executables and cannot deploy ordinary plugins; shared deployment ships the used Qt libraries and plugins ([deployment](https://doc.qt.io/qt-6/deployment.html#static-vs-shared-libraries)). Qt WebEngine is optional, so a Widgets/Quick application need not ship Chromium ([supported-platform exceptions](https://doc.qt.io/qt-6/supported-platforms.html#exceptions)).

**Inference:** A Qt Widgets/Quick application can have a moderate, controllable native payload with no managed/browser runtime, but the exact set of Qt, graphics, compiler, image, SQL, and QML components dominates size. Dynamic linking is the practical LGPL-compatible baseline for a proprietary app and should be measured after `windeployqt` pruning.

**Verified:** WPD can be consumed directly from a Windows C++ target, and Qt's worker-object pattern executes blocking work on a separate thread and returns results through queued signals; interruption is cooperative ([WPD C++ API](https://learn.microsoft.com/en-us/windows/win32/api/portabledeviceapi/), [QThread details and interruption](https://doc.qt.io/qt-6/qthread.html#details)).

**Inference:** Qt has the least language-boundary glue for WPD. That benefit comes with direct C++ ownership of COM pointers, stream buffers, cancellation, and thread safety, making sanitizers, RAII wrappers, and fault-injection tests important.

#### Persistence, security, and testing

**Verified:** Qt SQL ships a SQLite driver; Qt calls SQLite its best-tested in-process database across platforms, and binary Qt builds ship the SQLite plugin ([Qt SQL drivers](https://doc.qt.io/qt-6/sql-driver.html#supported-databases)). The driver operates on a single local file and has configurable lock timeout behavior ([QSQLITE](https://doc.qt.io/qt-6/sql-driver.html#qsqlite-for-sqlite-version-3-and-above)).

**Verified:** Qt Test provides unit tests, GUI mouse/keyboard simulation, data-driven tests, benchmarks, CTest integration, and CI-friendly output formats ([Qt Test](https://doc.qt.io/qt-6/qtest-overview.html)).

**Inference:** A normal Qt application and its plugins share full process authority. Avoiding Qt WebEngine removes web-content attack classes, but C++ memory corruption and native dependency vulnerabilities remain. A helper process can add fault containment if device inputs or drivers prove unstable.

#### Packaging, license, and maintenance trade-off

**Verified:** On Windows, `windeployqt` scans the executable and gathers Qt libraries, plugins, QML modules, and compiler runtime dependencies into an installation tree, but does not account for every third-party library and does not itself create the final installer ([Windows deployment tool](https://doc.qt.io/qt-6/windows-deployment.html#the-windows-deployment-tool)).

**Verified:** Under LGPLv3, a proprietary application is generally possible with dynamic linking, but distributors must provide LGPL notices/source access, permit replacement/relinking and reverse engineering for that purpose, and verify that no selected module is GPL-only; a commercial license is the alternative ([Qt licensing obligations](https://www.qt.io/licensing/open-source-lgpl-obligations)).

**Inference:** Qt's technical maintenance burden is conventional native C++/CMake plus per-platform installer/signing work. Its legal/compliance burden is uniquely higher in this set and should be resolved with counsel before prototyping proprietary distribution features.

**Inference:** Tauri and Electron provide the most integrated multi-platform artifact matrix. Avalonia, Flutter, and Qt all have credible release paths, but require more explicit composition of framework output with platform packaging. ## Security comparison

| Candidate | Verified controls | Product-specific inference |
| --- | --- | --- |
| Tauri | Per-WebView capabilities, plugin permissions/scopes, CSP guidance, and OS WebView security updates ([capabilities](https://v2.tauri.app/security/capabilities/), [WebView2 servicing](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)). | Keep device/filesystem/SQL operations behind narrow Rust commands. Do not load remote UI code or grant generic shell/filesystem write capability. |
| Electron | Context isolation and renderer sandbox defaults, CSP, IPC sender validation, navigation restrictions, and security fuses ([checklist](https://www.electronjs.org/docs/latest/tutorial/security#checklist-security-recommendations)). | Treat the renderer as untrusted even for local content; use a typed preload API. Fast Electron upgrades are an operational security requirement, not optional maintenance. |
| Avalonia | Native-rendered controls and normal .NET/native process model; MSIX can provide signed integrity and optional app-container behavior ([Avalonia overview](https://docs.avaloniaui.net/docs/welcome), [MSIX](https://learn.microsoft.com/en-us/windows/msix/overview)). | There is no renderer sandbox. Validate imported paths/metadata at domain boundaries and consider an unprivileged helper only if device/native fault containment is needed. |
| Flutter | AOT Dart UI plus native runner/plugins; isolates separate Dart mutable memory ([source](https://github.com/flutter/flutter), [isolates](https://docs.flutter.dev/perf/isolates)). | Isolates are concurrency boundaries, not OS security boundaries. Native plugin inputs and channel messages still need validation. |
| Qt | Native C++ process and optional dynamically loaded plugins; no browser component unless selected ([deployment](https://doc.qt.io/qt-6/deployment.html), [platform exceptions](https://doc.qt.io/qt-6/supported-platforms.html#exceptions)). | Reduced web attack surface, but greatest memory-safety exposure in application-owned native code. Minimize parsers and raw buffer ownership in the MTP layer. |

**Inference:** For this offline/local product, the most important common controls are signed installers and updates, strict validation of paths and device metadata, no remote executable UI/content, atomic job-state transitions, and tests for disconnect/cancel/crash behavior. Web stacks add an IPC privilege boundary that can be a useful control if configured narrowly; native-rendered stacks remove that web boundary but do not automatically sandbox backend code.

**Verified:** WPD exposes stream cancellation, but physical-device behavior is outside every candidate's UI test tooling ([WPD data stream](https://learn.microsoft.com/en-us/windows/win32/api/portabledeviceapi/nn-portabledeviceapi-iportabledevicedatastream)).

**Inference:** A transport contract is the highest-leverage test seam. A smaller Windows-only suite should exercise at least representative real MTP devices and the packaged application, because no candidate's UI test framework can emulate driver/device quirks.

## Decision-relevant conclusions, without a stack decision

1. **MTP does not force a specific UI stack.** WPD is a Windows COM streaming API with cancellation and commit semantics ([WPD interfaces](https://learn.microsoft.com/en-us/windows/win32/api/portabledeviceapi/), [data stream](https://learn.microsoft.com/en-us/windows/win32/api/portabledeviceapi/nn-portabledeviceapi-iportabledevicedatastream)). Qt and Avalonia have the shortest in-process route; Tauri has a first-party Microsoft Rust binding route; Electron and Flutter require more explicit native bridge machinery. A helper process remains available to every candidate if crash containment outweighs IPC complexity.
2. **Transfer architecture dominates responsiveness and recovery.** Every candidate can move work off the UI thread, but durable resumable/cancellable job behavior must be designed above the framework. SQLite is suitable for local durable metadata and job state ([SQLite use cases](https://www.sqlite.org/whentouse.html), [durability](https://www.sqlite.org/transactional.html)).
3. **Runtime footprint is a distribution-mode trade, not a reliable single ranking.** Electron always owns Chromium and Node; Flutter owns its engine; self-contained Avalonia owns .NET and Skia; Qt owns selected native libraries/plugins; Tauri normally shares the OS WebView but an offline/fixed WebView2 mode can add a large runtime ([Electron security/runtime composition](https://www.electronjs.org/docs/latest/tutorial/security#general-guidelines), [.NET modes](https://learn.microsoft.com/en-us/dotnet/core/deploying/), [Qt deployment](https://doc.qt.io/qt-6/deployment.html), [WebView2 distribution](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)). Measure signed online and offline installers plus idle/active memory in a prototype.
4. **Packaging maturity separates integrated bundlers from build outputs.** Tauri and Electron expose broad installer matrices directly ([Tauri distribution](https://v2.tauri.app/distribute/), [Electron Forge makers](https://www.electronforge.io/config/makers)). Avalonia/.NET, Flutter, and Qt produce viable application outputs but leave more platform packaging composition to project tooling ([.NET publishing](https://learn.microsoft.com/en-us/dotnet/core/deploying/), [Flutter deployment](https://docs.flutter.dev/deployment/windows), [Qt deployment](https://doc.qt.io/qt-6/deployment.html)). This is release-engineering work, not a blocker, and should be priced explicitly.
5. **Security models differ rather than simply rank.** Tauri and Electron provide renderer/native privilege boundaries but require careful IPC and web-content configuration ([Tauri capabilities](https://v2.tauri.app/security/capabilities/), [Electron security](https://www.electronjs.org/docs/latest/tutorial/security)). Avalonia, Flutter, and Qt avoid a browser renderer yet normally run UI and native backend with the same process authority. Qt additionally carries C++ memory-safety and LGPL/commercial-license considerations ([Qt obligations](https://www.qt.io/licensing/open-source-lgpl-obligations)).
6. **The likely discriminators for a later decision are team capability and prototype evidence.** A focused spike should implement the same thin vertical slice in the leading candidates: enumerate one MTP device, copy one large file with progress/cancel, persist and recover a job, package a signed Windows installer, and run domain plus packaged smoke tests. Record installer sizes in online/offline modes, idle and transfer memory, throughput, disconnect behavior, CI build time, native bridge code volume, and update workflow. That evidence can resolve the remaining inferences without prematurely selecting the product stack.

## Source quality and limitations

Sources are first-party framework/platform documentation and upstream source repositories. The WPD documentation is authoritative but some pages are old because the API is a long-standing Win32 COM surface. Framework and support-policy pages are living documentation and can change after the research date. No third-party benchmark was used because generic "hello world" size or memory comparisons would not represent a signed ROM manager containing SQLite, transfer code, assets, and native MTP support.
